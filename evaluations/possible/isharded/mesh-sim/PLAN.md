# Local mesh simulator for the iSharded ↔ Aven live-data test

A controllable, model-backed mesh that reproduces iSharded's **observable interface
and behaviour** so the whole Aven live-data path can be validated on our own hardware —
before, and independently of, AuXFire confirming a real test. It also gives us a rig for
the "larger tests" question (spin up more stages than iSharded's 7).

This goes with [`../isharded_route.aven`](../isharded_route.aven), the poller
[`../isharded_poller.py`](../isharded_poller.py), and [`../LIVE_DATA_PLAN.md`](../LIVE_DATA_PLAN.md).
Nothing here is built yet.

## Why a simulator (and why a second host)

The point of the Aven route model is that **the network dominates** a token's time (the
real run: 884 ms network, 89% of each token, ~147 ms per link). An all-local Docker/kind
mesh has **loopback hops — effectively 0 ms**, so on one machine the sim reproduces the
*structure* but not the thing the model is actually about.

A second physical host — the Linux server, reached over **Tailscale** — puts **real network
latency** on the hops to it. That makes the `avenc stream` thresholds fire on genuine
jitter, not synthetic numbers, and makes this a faithful rehearsal of the real mesh. The
same Tailscale path is how we'd reach the real iSharded mesh later, so none of it is throwaway.

## Topology (agreed)

```
  Local machine (Windows, this repo)          Linux server (over Tailscale)
  ┌───────────────────────────────┐          ┌──────────────────────────────┐
  │ kind cluster                  │          │ worker-5  (real cross-host    │
  │   worker-1  (model 1)         │          │            hop, real latency) │
  │   worker-2  (model 2)         │  Tailscale│ coordinator  /admin/status   │
  │   worker-3  (model 3)   ◄─────┼──────────┼─► /admin/inventory           │
  │   worker-4  (model 4)         │          │ monitor:  poller | avenc stream│
  └───────────────────────────────┘          │ Nova:     ALARM → Discord     │
                                              └──────────────────────────────┘
```

- **Workers 1–4**: the four local ~2–3 GB models, in `kind`. (Stage 1 runs stubs — no model.)
- **Worker 5**: on the server — a real cross-host stage, so at least one link carries real latency.
- **Coordinator / monitor / Nova**: on the server (always-on). Aven's alarms flow out through Nova to Discord.

## The API contract (must match the poller, unmodified)

The coordinator exposes the shape [`../isharded_poller.py`](../isharded_poller.py) already
reads, so `isharded_poller.py --raw` and the monitor work without code changes:

- `GET /admin/status` → `metrics.tokens_per_second_ema`, `active_plan.estimated_tokens_per_second`,
  `route[]` (each stage's `worker` + `layers`), and `workers[].runtime.telemetry`
  (`compute_ms_ema`, `downstream_ms_ema`, `phases_ms`, `activation_bytes_sent`).
- `GET /admin/inventory` → per-node peer RTT (real, from Tailscale), and CPU/GPU load where reported.
- Each worker: `POST /infer` (returns output + timing) and `POST /internal/diag/probe`
  (the 100-byte link probe iSharded uses).

Because the contract matches, **switching this sim for the real iSharded mesh is a change of
endpoint URL and key — nothing else.**

## Components

| Component | Stage 1 (stub) | Stage 2+ (real) |
|---|---|---|
| **worker** | returns synthetic-but-plausible `compute_ms` + sleeps a modelled hop time | loads one model (runtime TBD — Ollama / llama.cpp / transformers), real inference timing |
| **coordinator** | drives the token loop over the route, aggregates `/admin/status` in the contract shape | same |
| **monitor** | `isharded_poller.py \| avenc stream <generated route model>` with the provisional thresholds | same |
| **route model** | generated by `gen_route.py` to match the running stage count (we proved Aven solves 500 stages in 77 ms) | same |
| **Nova** | — | subscribes to the monitor's `ALARM` lines, posts to Discord |

## Staged build (each stage proves one thing)

1. **Stub mesh, local only** — N worker stubs + coordinator in `kind`, poller → `avenc stream` → `ALARM`.
   *Proves the plumbing end-to-end. Model-independent; no runtime decision needed.*
2. **Real models** — swap stubs for the 4 models' inference. *Real per-stage compute.*
3. **Cross-host over Tailscale** — move worker-5 + coordinator + monitor to the server.
   *Real network latency on a hop; the network-share numbers become meaningful.*
4. **Scale + fault injection** — more stages; kill a worker mid-run; watch HOLD / `ALARM`,
   and Nova posting it. *The "larger tests", and the detect→notify loop.*

## Networking (Tailscale)

- Both hosts on the same tailnet. The coordinator binds to the server's Tailscale address.
- The poller reaches `http://<server-tailscale-ip>:<port>/admin/status`; the key stays in
  `$ISHARDED_KEY` (env only — never in the compose file, the CSV, or the repo).
- `kind` on Windows exposes worker ports via port-mappings / an ingress the coordinator can reach.
- `/admin/inventory` RTTs come from real Tailscale pings between nodes.

## Reuse

- **`gen_route.py`** (prototype in scratchpad) already emits an N-stage `route.aven`; it becomes the
  coordinator's "write the model for the current route" step.
- **`k8s/` controller pattern** (`aven_controller.py` + `workload_adapter.py`) is a working template
  for an adapter → Aven → action loop in a cluster — the monitor follows the same shape.
- **`isharded_poller.py`** is the monitor's data tap, unchanged.

## Deployment & Nova integration (non-disruptive)

Nova runs live on the server, so integration must not interrupt her.

- **Files to the server:** at stage 3, copy `mesh-sim/` to the server (scp/rsync over Tailscale)
  and bring the mesh up there as its **own compose stack**, separate from Nova's.
- **Connecting Nova:** join the two stacks on a shared **external Docker network** (or the monitor
  reaches Nova at her host address `127.0.0.1:8740` / `host.docker.internal:8740`). Do **not** loosen
  Nova's sandbox (`read_only`, `cap_drop: ALL`, `no-new-privileges`).
- **Picking up the API link without downtime for the rest:** set Nova's env/config for the link, then
  restart **only** her service — `docker compose -f deploy/docker-compose.yml up -d --no-deps nova`
  (Nova's own documented single-service update). Her supporting services (nllb, whisper, tts, searxng)
  and the co-hosted Alliance Auth / Forgejo stacks keep running; only Nova blips for a few seconds.
- **Alarm path:** the monitor posts each `avenc stream` `ALARM` to Nova's `:8740` API (API-key auth)
  so she announces it; or, with zero Nova change, straight to a Discord webhook. A small `/notify`
  endpoint in Nova's repo is the cleanest, but that's a change on her side.
